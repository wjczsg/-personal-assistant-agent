# 学习与求职中的个人资料助理

一个面向学生与求职者的 AI 应用开发实践项目。用户可以上传自己的学习笔记、项目资料等文本，在聊天中基于资料提问，也可以让助理提出学习或求职待办建议；新增待办须经用户在后续消息中明确确认。项目面向单用户演示，仓库提供容器部署配置，但尚未实现可供多人注册使用的线上产品。

项目的重点不是把所有事情交给模型自动执行，而是把**个人资料检索、工具调用和用户确认**串成一条可检查的工作流。计算器、时间和天气等通用工具仍保留，但不再作为项目的主要定位。

## 目标场景与当前范围

- **围绕资料提问**：上传学习笔记、项目说明或求职准备资料后，提问相关内容；Agent 可按需检索文档片段，并依据片段组织回答。
- **把建议变成行动**：根据对话或文档内容提出一条待办提案，展示内容后等待用户回复“确认”或“取消”；只有确认后才写入待办。
- **记住较稳定的背景**：在模型调用记忆工具时保存长期目标、偏好或个人背景；后续对话可检索有效记忆。

目前文档只支持 UTF-8 `.txt` / `.md`，可用文本文件模拟笔记或求职资料；PDF、Word、简历解析、岗位匹配、自动制定完整学习计划和用户注册登录**尚未实现**。

## 项目亮点（可用于简历梳理）

- **Agent 编排**：基于 OpenAI Chat Completions 兼容接口实现模型请求、工具选择和最多三轮连续工具调用。
- **工具注册与 Function Calling**：通过工具注册表统一维护工具定义和执行映射，支持计算、时间、天气、待办、记忆和文档检索。
- **基础 RAG**：实现文档上传、分块、向量索引、按需检索和来源返回，文档索引与长期记忆使用独立 Chroma 集合。
- **长期记忆管理**：使用 SQLite 保存记忆原文和状态，使用 Chroma 做语义检索；检索前后分别进行用户隔离、有效状态和距离阈值过滤。
- **动态记忆检索**：通过 `should_search_memory()` 让不含长期背景线索的天气、待办、计算和普通问候跳过记忆检索；个人目标、职业方向等问题才进入检索流程，轻量模型兜底判为记忆问题时也会尝试检索。
- **动态工具路由**：`tool_router.py` 优先用本地规则识别天气、待办、文档、记忆和普通聊天；`routing_service.py` 可对部分未命中的问题调用轻量模型兜底分类。组合问题合并路由工具，兜底分类只开放只读工具。
- **跨轮补充信息**：模型追问缺失参数时，将原任务和追问保存到 SQLite；用户下一条回复可继续原任务的路由与工具调用，取消或提出新任务时清除待补充状态。
- **上下文输入预算**：每轮模型请求前估算消息与工具定义的体积，优先保留当前问题和本轮工具调用链，再按预算选择相关记忆与最近的完整对话轮次。
- **滚动历史摘要**：当旧问答放不进输入预算时，将已完成的旧轮次分批压缩并保存在 SQLite；模型同时看到摘要与最近原文，而不是直接丢失全部旧背景。
- **Human-in-the-loop 工作流**：新增待办先生成 `pending` 提案，用户下一条消息明确确认后才真正写入待办表；该确认机制目前不覆盖完成、修改、删除待办或保存记忆。
- **可测试性**：核心数据库、记忆状态、RAG、工具调用、天气和待办确认流程均有自动化测试。

这些亮点描述的是当前代码已经实现的能力。仓库虽有 Docker Compose、部署和回滚脚本，但尚不具备生产环境的多用户认证与完整运维能力。

### 动态工具路由的作用与收益

动态工具路由不是一个新的业务工具，而是 Agent 调度层。它在请求大模型之前，先根据用户问题判断可能涉及的业务领域，再把当前问题需要的工具子集发送给模型。

改造前，即使用户只问“北京明天天气怎么样”，模型也可能收到计算器、天气、待办、文档和记忆等全部工具定义。改造后，流程变为：

```text
用户问题 → tool_router.py 本地规则 → 必要时 routing_service.py 轻量模型兜底
         → 选择工具子集 → Agent 请求主模型
```

例如：

```text
北京明天天气怎么样？
→ weather 路由
→ 只发送 get_weather

如果明天下雨，就提醒我带伞
→ weather + todo 路由
→ 合并发送天气工具和待办工具

根据上传的文档帮我添加一个待办
→ document + todo 路由
→ 合并发送文档检索工具和待办工具

你好，今天心情怎么样？
→ chat 路由
→ 不发送 tools 字段
```

这项设计带来的具体收益包括：

- **减少上下文和 Token 消耗**：普通聊天不再携带全部工具定义；天气问题只携带天气工具，工具数量增加后节省效果会更加明显。
- **降低工具误调用概率**：模型看到的候选工具更少，问天气时不容易误调用待办、文档或记忆工具。
- **缩小可调用工具范围**：普通聊天通常不会开放保存记忆、删除待办等工具；本地规则命中保存记忆相关关键词时才开放 `save_memory`，轻量模型兜底只开放只读工具。关键词可能误判，待办本地路由目前也会开放整组待办工具，不能把路由当作操作级权限控制。
- **改善代码可维护性**：路由规则集中在 `tool_router.py` 中，`agent.py` 主要负责消息组织、模型请求和工具执行，新增业务工具时不必继续堆积 Agent 主流程。
- **支持多工具组合任务**：一个问题可以同时命中多个路由；模型可以在后续轮次读取工具结果并继续调用工具。

需要区分“记忆检索”和“保存记忆”：用户询问“我的职业目标是什么”时，Agent 可以在请求模型前内部检索已有记忆，但不会把会写入数据库的 `save_memory` 工具开放给模型。本地规则命中“请记住”“记下来”“长期记忆”等关键词时会开放保存工具；这仍是关键词判断，不能保证每次都准确理解用户意图。

当前先使用轻量关键词规则：命中明确业务路由时不增加模型请求；规则未命中、消息符合疑问或请求形式、长度至少 6 个字符且不是明显问候时，`routing_service.py` 才尝试用模型输出单个 JSON 路由。分类失败会保留 `chat` 路由；分类成功也只开放天气、待办查询或文档检索等只读工具，记忆路由不开放 `save_memory`。这是一层有限的兜底，不会把所有工具重新开放，也不能保证识别所有隐含表达。规则中的“完成”“删除”“修改”等词还可能误命中待办领域，后续需要更细的操作识别与评测。

从项目经历角度，这部分可以概括为：

> 设计并实现规则优先、轻量模型兜底的动态工具路由，将请求分为天气、待办、文档、记忆和普通聊天等场景；按需暴露工具，并将兜底分类限制为只读工具。

## 已实现的功能

- **网页对话**：FastAPI 提供聊天接口和简洁的 Web 页面。
- **文档问答（基础 RAG）**：网页可上传不超过 1 MB 的 UTF-8 `.txt` / `.md` 文档，原文保存在 SQLite；上传后自动分块并写入 Chroma 的 `document_chunks` 集合，与长期记忆分开。模型需要文档依据时，可调用检索工具获取当前用户的片段，再根据原文回答。
- **Function Calling**：模型按需选择计算器、当前时间、天气、待办操作、保存长期记忆和检索上传文档等工具；Agent 会先根据路由缩小本轮工具范围，再让模型在范围内选择。
- **动态工具路由**：本地规则命中天气问题时开放天气工具，命中待办时开放待办工具组，命中文档时开放文档检索，命中保存记忆相关关键词时开放 `save_memory`；组合请求合并多个路由。规则未命中的部分问题可经轻量模型兜底分类，兜底结果只开放只读工具；普通聊天没有候选工具时省略 `tools` 字段。
- **待补充任务**：业务问题缺少城市、待办编号等必要信息时，模型可用 `【待补充信息】` 标记追问；Agent 将原请求和问题写入 `pending_clarifications`。简短回复会与原请求合并后重新路由；较复杂的回复先由轻量模型判断是补充、取消还是新任务。待补充状态按用户隔离，24 小时后失效，完成或取消后清除。
- **上下文预算管理**：从 SQLite 读取最多 100 条历史作为候选；请求模型前按输入预算保留最近的完整问答轮次，较早历史不发送但仍留在数据库。每次工具调用后重新检查预算。
- **历史对话摘要**：旧历史超出预算或最近 100 条候选范围时，调用同一模型生成滚动摘要；单次聊天最多发起三次摘要请求，摘要失败则维持旧状态并继续按原有预算聊天。
- **聊天确认添加待办**：模型调用 `propose_todo` 时只保存一条待确认提案，不立即添加待办。下一条消息回复“确认”或“取消”才处理；有多条待确认提案时需回复“确认提案 #编号”等明确指令。原来的直接添加函数仍在代码中，但不再作为模型工具开放。
- **待办查询**：可以查询未完成、已完成或全部待办；默认只显示未完成，完成的待办不会丢失。
- **删除待办**：明确指定待办编号后可永久删除；按内容删除时先查全部待办，不能唯一确定时不删除。
- **修改待办**：按编号修改文字，保持原有完成状态；目标不明确时先查列表或询问用户。
- **连续工具调用**：模型可在后续轮次读取上一轮工具结果，再决定是否调用其他工具；用户在下一条消息确认提案后才真正添加待办。主对话的工具循环最多请求模型三轮，路由分类和历史摘要可能额外请求模型。若模型在同一响应中返回多个工具调用，当前代码会顺序执行这些调用，不会在每个调用之间重新询问模型；因此条件任务是否先读结果再行动仍依赖模型正确拆分轮次。
- **天气查询**：支持当前天气，以及城市当地今天起未来 16 天内的每日预报；可以使用“明天”“后天”或 `YYYY-MM-DD` 日期。
- **动态长期记忆**：SQLite 保存最近对话、待办和长期记忆原文；Chroma 为长期记忆建立向量索引。Agent 会先通过 `should_search_memory()` 判断问题是否可能需要长期背景，只有需要时才检索；结果进入 Agent 前还会过滤失效记忆和超过距离阈值的结果。
- **便于学习**：核心模块有中文注释，并包含天气、连续工具调用、记忆状态与检索等自动化测试。

## 工作流程

```text
浏览器 → FastAPI /api/chat → Agent
                            ├─ 从 SQLite 读取最近对话
                            ├─ 检查 pending_clarifications
                            │   └─ 补充原任务／取消／改为新任务
                            ├─ 若是待办提案确认/取消，由后端直接处理
                            ├─ 动态工具路由
                            │   └─ 本地规则 → 必要时轻量模型兜底 → 选择工具子集
                            ├─ 判断是否需要长期记忆
                            │   └─ 需要时：Chroma 检索 → SQLite 状态过滤 → 距离阈值过滤
                            ├─ 组装动态系统提示词与工具定义
                            ├─ 旧历史超预算时更新滚动摘要，并保留最近问答原文
                            └─ 请求大模型
                                ├─ 直接回答
                                └─ 按需调用工具注册表中的工具
                                    ├─ 检索当前用户的 document_chunks → 提供片段供模型回答
                                    └─ 计算器、天气、待办等 → 根据结果回答

新增待办：模型调用 propose_todo → SQLite 保存 pending 提案 → Agent 展示提案
          → 用户下一条消息明确确认/取消 → 确认时写入 todos，取消时不写入
```

待办确认由后端根据用户后续发送的明确回复处理，不是模型在同一轮对自己的提案作出批准。重复确认不会重复添加待办；若同时存在多条待确认提案，需要指定提案编号。该流程**只覆盖新增待办**，不覆盖修改、完成或删除待办。

待补充任务与待办提案是两种不同状态。例如“查询明天天气，如果下雨就提醒我带伞”缺少城市时，Agent 会保存原请求和追问；下一条只回复“福州”，路由器仍能按完整任务开放天气工具。修改待办时补充“#5”也使用同一流程。回复“算了”会取消待补充任务；明确的新问题会替换旧任务。每个用户同时只保存一个待补充任务。该功能依赖模型使用追问标记，后端也兼容部分未带标记的常见追问措辞；它不能保证识别所有自由表达。

上下文预算由 `CONTEXT_INPUT_BUDGET_TOKENS` 控制，默认 12000。这是项目为控制输入量设定的目标，**不是模型实际上下文上限**。Agent 从 SQLite 读取最多 100 条历史消息作为候选；每轮调用主模型前，先为系统提示词、当前问题、本轮已产生的工具调用与结果、动态路由后的工具定义留空间，再放入相关长期记忆和最近的完整对话轮次。超出的较早对话仍保留在 SQLite，本轮暂时不发送；预算不能容纳当前问题或本轮工具结果时会提示用户。长期记忆最多检索 3 条，文档工具最多返回 3 个片段，主对话的工具循环最多请求模型 3 轮。

预算使用 UTF-8 字节数做**保守 Token 估算**，并非 DeepSeek 实际计费 Token；真实用量以模型响应中的 `usage.prompt_tokens` 为准。多轮工具调用后会重新计算预算，工具调用与对应结果会成组保留。

较早的完整问答放不进预算时，`history_summary.py` 从 SQLite 按消息编号读取旧轮次，调用当前配置的模型把“旧摘要 + 新一批旧问答”压缩成新摘要；`conversation_summaries` 表保存每个用户的摘要和最后处理的消息编号。之后发给主模型的是**摘要 + 未总结的最近原文 + 当前问题**，已经总结的原文不会重复发送。摘要更新与编号推进在同一数据库事务中完成；并发请求不会覆盖较新的摘要。即使消息早于最近 100 条候选，也能分批补入摘要。摘要请求本身有大小限制，每次用户请求最多发起三次摘要模型调用（失败也计数），避免一次聊天无限追加模型调用。

这项功能只压缩**对话历史**，不是长期记忆，也不会把每句话写进 Chroma。原始聊天仍留在 SQLite；摘要是有损的背景概括，可能遗漏细节，重要事实应以原始资料或明确的长期记忆为准。生成摘要需要额外模型请求，会增加延迟和费用；失败时不推进处理位置，当前聊天仍按输入预算裁剪旧历史继续进行。它也不能解决当前问题或本轮工具结果本身超限。自动化测试覆盖流程，但尚未用真实模型的 `usage.prompt_tokens` 和长对话事实保持率做系统评测。

长期记忆并不是把所有聊天内容都写进向量库。只有本轮开放 `save_memory` 且模型实际调用时，才会尝试保存用户的长期目标、稳定偏好或个人背景：先写入 SQLite，再写入 Chroma；若向量索引失败，SQLite 原文仍会保留并返回失败提示。后续相关提问时，Agent 可检索有效记忆作为回答参考。上传的文档片段使用另一集合，不会变成长期记忆。

记忆状态以 SQLite 为准：需要检索时，Agent 先取得当前用户的有效记忆编号，再让 Chroma 按语义排序；返回的片段若不在有效编号中，或 `distance` 大于 `settings.memory_distance_threshold`，就不会送入 Agent。若靠前的结果都已失效或被阈值过滤，检索会逐步扩大候选范围，避免漏掉排在后面的有效记忆。当前默认距离阈值为 `0.9`，这是根据现有数据得到的初始值，可通过 `.env` 中的 `MEMORY_DISTANCE_THRESHOLD` 调整。旧版数据库会在服务启动时补上 `status` 和 `superseded_by` 字段，已有记忆默认保持有效。当前只具备数据库层按编号标记“被取代”的能力，**尚未提供网页操作或 Agent 工具来自动标记旧记忆**；仅说“旧目标作废”还不能保证数据库状态被修改。

动态记忆检索解决的是“不是每个问题都需要长期记忆”的问题。修改前，用户发送“你好”、天气或待办问题时，Agent 也会尝试查询长期记忆，并可能把职业目标等无关内容加入上下文。现在 `should_search_memory()` 会先进行低成本关键词门控：不含长期背景线索的普通问候、天气、计算和待办问题通常跳过记忆检索；职业目标、个人背景、长期计划和稳定偏好等问题才继续查询。轻量模型兜底若判为 `memory`，也会强制尝试检索。即使进入 Chroma 检索，结果还必须通过距离阈值过滤，避免 Chroma 在没有真正相关内容时返回“相对最接近”的无关记忆。

这项优化带来的具体收益包括：

- **减少上下文干扰**：天气问题不再自动带入职业目标，普通问候也不会加载个人背景。
- **降低不必要的计算和 Token 消耗**：不需要记忆的问题跳过向量检索，也不会把无关记忆发送给大模型。
- **降低模型误解风险**：模型看到的长期记忆与当前问题相关性更高，减少被旧信息或无关信息影响的可能。
- **提高检索结果质量**：距离阈值可以过滤“虽然是最接近结果、但实际上并不相关”的记忆。

当前门控仍采用轻量关键词策略，距离阈值 `0.9` 也只是基于现有样本得到的初始值。关键词可能漏掉表达方式，阈值过严可能漏掉相关记忆，阈值过宽则可能保留无关记忆，因此后续仍需要使用更多正例和负例进行校准。

文档检索由模型通过 `search_uploaded_documents` 工具按需选择：普通聊天不预先查询文档；模型调用工具后，Python 才从 `document_chunks` 中检索当前用户最多 3 个片段。一条用户消息最多实际执行一次文档检索；如果模型重复请求，额外调用会收到简短提示，不会再次访问向量库。返回给模型的检索结果整体最多 2400 UTF-8 字节，包含原文、文件名、文档编号和片段编号；`truncated: true` 表示只返回了部分片段，不能据此概括整篇文档。工具参数只有检索问题，用户编号由 Agent 提供，模型不能指定其他用户。工具返回空结果或检索故障时，模型应说明缺少依据，而不是猜测文档内容。模型是否正确选择工具仍需测试，不能保证每次都选对。

模型请求和多轮工具调度目前主要由项目自身实现；计算器工具已作为小范围示例使用 LangChain 的 `langchain-core` 包装。项目**不是**整体基于 LangChain 构建的。

## 本地运行

需要 Python 3.12。以下命令在 Windows PowerShell 中运行，先进入本项目根目录：

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
```

编辑 `.env`，填写兼容 OpenAI Chat Completions 接口的模型配置：

```dotenv
LLM_BASE_URL=https://api.openai.com/v1
LLM_API_KEY=你的密钥
LLM_MODEL=你的模型名称
CONTEXT_INPUT_BUDGET_TOKENS=12000
MEMORY_DISTANCE_THRESHOLD=0.9
```

启动服务：

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

打开 <http://127.0.0.1:8000/> 使用网页；接口文档位于 <http://127.0.0.1:8000/docs>。停止服务按 `Ctrl+C`。

分块函数优先选择段落或句末边界，默认每块最多 500 个字符、相邻块重叠约 50 个字符。上传时先把原文保存到 SQLite，再自动分块并写入 Chroma；接口等索引完成后才返回。页面会显示文档编号、是否索引成功，以及成功时的块数。第一次计算嵌入向量可能需要较长时间，请等待页面状态更新。

若页面显示“已保存但自动索引失败”，原文仍在 SQLite。可在 <http://127.0.0.1:8000/docs> 找到 `POST /api/documents/{document_id}/index`，填入页面显示的文档编号，并提交 `{"user_id":"web-user"}` 重试。重复索引会更新相同片段，不会无限新增。以前上传但尚未索引的文档不会因这次代码更新而自动补建索引，也可以用该接口补建。

建好索引后，回到网页聊天框，提出一个能从文档中找到答案的问题。Agent 会把检索片段连同问题交给模型，提示模型根据片段回答并说明出处；它仍使用原来的 `/api/chat` 接口，不需要切换页面或选择专门模式。实际回答是否正确，仍需对照原文检查。

需要单独检查检索结果时，可在 <http://127.0.0.1:8000/docs> 调用 `POST /api/documents/search` 并提交 `{"user_id":"web-user","query":"文档里提到了什么？"}`。接口返回最多 3 个相关片段及文件名、文档编号和块序号；它只搜索该用户的**已索引**文档，不调用大模型生成答案。网页上的临时检索测试区已移除。Chroma 总会返回相对最接近的片段，所以命中不一定真正相关，需要核对原文。

> 如果不填写 `LLM_API_KEY`，项目会进入演示模式：可以启动网页、上传文档并保存对话，但聊天时不会调用大模型、自动选择工具，也不会执行 Agent 的长期记忆或文档检索与问答。完整功能需要配置可用的模型及密钥。

## 可以试试

在网页中依次提问：

1. `12 * 8 等于多少？`
2. `北京明天的天气怎么样？`
3. `帮我添加一个待办：周末整理简历。`（先显示提案；下一条消息回复 `确认` 才会真正添加，也可回复 `取消`）
4. `我还有哪些待办？`
5. `把刚才整理简历的待办标记为完成。`
6. `我已经完成了哪些待办？`
7. `列出我的全部待办。`
8. `删除待办 #1。`（请换成列表中实际存在的编号；删除后无法恢复）
9. `把待办 #2 改成：周日完善简历。`（请换成列表中实际存在的编号）
10. `请记住：我毕业后想从事 AI 应用开发。`
11. `我毕业后想做什么方向的工作？`

第 10、11 句用于观察长期记忆的保存与检索。模型负责决定是否调用工具，因此实际调用情况取决于所配置模型的 Function Calling 能力。

测试动态长期记忆时，可以分别提问：

1. `你好`：不应因为普通问候而加入长期记忆。
2. `北京明天的天气怎么样？`：天气问题不应查询长期记忆。
3. `我未来想从事什么方向？`：应尝试检索相关的职业目标记忆。
4. `我喜欢什么音乐？`：可以触发检索，但如果没有足够接近的记忆，不应把无关结果交给模型。

长期记忆检索目前采用轻量关键词门控和 Chroma 距离阈值，不能仅凭一个测试问题证明所有自然语言表达都能被正确分类。

测试文档问答时，上传一份内容独特的新文档，确认页面显示“已保存并建立索引”，然后直接问一个文档里有明确答案的问题：前端应显示“已使用：search_uploaded_documents”，回答应能对应到文档原文。再问天气、待办等无关问题，观察它是否没有调用文档检索；也试一个文档里没有答案的问题，检查模型是否承认缺少依据。

测试“资料 → 行动”时，可在文档中写一项明确的学习任务，再问“根据我上传的资料，帮我把这项任务加入待办”。检查 Agent 是否先检索资料并展示待确认提案；此时查询待办不应看到新记录。回复 `确认` 后再查待办，确认只新增一条。模型是否选中检索或提案工具仍受模型能力影响，不能仅凭一条成功案例认定流程始终可靠。

测试跨轮补充时，可先问“查询明天天气，如果下雨就提醒我带伞”，等助理追问城市后只回复“福州”；也可先要求修改一条未指定编号的待办，等追问后回复实际编号。可再用“算了”和一个无关新问题检查旧任务是否被清除。

## 当前边界

这是学习项目，不是已经具备生产环境安全措施的多用户服务。网页从浏览器本地存储读取用户标识，缺省为 `web-user`；接口信任请求中传入的 `user_id`，尚无登录认证。网页的“清空对话”只清除当前页面中的消息，不删除 SQLite 历史；聊天响应里的 `memory_count` 是本轮读取的旧对话消息数量，不是长期记忆条数。

系统提示词定位为学习与求职资料助理，但当前网页仍使用“小熊日常助手”的品牌文案，并以天气、计算和待办作为主要快捷示例；资料问答可以通过上传和聊天完成，页面文案尚未同步到项目定位。

目前只有“新增待办”走后续消息确认，完成／删除／修改待办和保存长期记忆仍沿用模型工具流程。“确认”与“取消”需明确回复，多条待确认提案需带编号，暂不支持在确认前直接编辑提案文字。待补充状态依赖追问标记或有限的文本识别；简短回复通常按补充处理，复杂回复需要一次额外分类请求，分类失败时按新任务处理以避免误执行旧任务。同一模型响应若返回多个工具调用，代码会顺序执行，条件任务仍需验证模型是否将依赖步骤分到不同轮次。工具循环达到三轮上限后可能已执行工具但只返回次数限制提示。

天气工具不支持历史天气或指定小时。长期记忆尚未提供去重、面向用户的查看／纠错／删除操作；SQLite 中标为失效的记忆不会进入 Agent 上下文，但旧向量仍留在 Chroma。记忆检索依赖关键词门控与初始距离阈值，路由虽有轻量模型兜底，规则命中后的宽泛关键词仍可能误判，兜底也只选择单个业务类别。

上传请求会等待向量索引完成，索引失败时原文保留，可手动重试，但没有后台重试任务。文档检索没有相关性阈值，可能漏掉正确片段或返回无关片段；模型给出的来源尚未由程序逐条核验。Chroma 当前使用默认 Embedding 模型，中文语义检索效果仍有优化空间。
